# Tools & Permissions

ANAS CLI uses tools to inspect project files, modify code, execute terminal commands, search the codebase, and inspect Git repositories.

Tool availability depends on the selected interaction mode. Operations are also subject to permissions and safety guardrails.

## Available tools

ANAS CLI currently provides eight registered tools.

| Tool          | Purpose                                               |
| ------------- | ----------------------------------------------------- |
| `read_file`   | Read file contents.                                   |
| `write_file`  | Create or overwrite files.                            |
| `edit_file`   | Replace specific text in existing files.              |
| `bash`        | Execute terminal commands using Windows CMD.          |
| `glob`        | Find files matching a glob pattern.                   |
| `list_dir`    | List directory contents.                              |
| `search_code` | Search project files for matching code or text.       |
| `git`         | Inspect repository status, diffs, logs, and branches. |

## Tool access by mode

ANAS CLI provides three interaction modes.

| Tool          | Ask | Agent | Plan |
| ------------- | --- | ----- | ---- |
| `read_file`   | Yes | Yes   | No   |
| `write_file`  | No  | Yes   | No   |
| `edit_file`   | No  | Yes   | No   |
| `bash`        | No  | Yes   | No   |
| `glob`        | Yes | Yes   | No   |
| `list_dir`    | Yes | Yes   | No   |
| `search_code` | Yes | Yes   | No   |
| `git`         | No  | Yes   | No   |

### Ask mode

Ask mode supports read-only code exploration.

```bash id="nsgz7c"
npm run dev -- chat --mode ask
```

Available tools:

- `read_file`
- `search_code`
- `glob`
- `list_dir`

Ask mode cannot invoke file-writing, editing, terminal, or Git tools through its tool allowlist.

### Agent mode

Agent mode supports the full coding workflow.

```bash id="rsxyid"
npm run dev -- chat --mode agent
```

Agent mode can access all eight registered tools, subject to permissions and guardrails.

It can inspect files, modify code, execute commands, search the project, and inspect Git state.

### Plan mode

Plan mode is intended for discussing implementation approaches before making changes.

```bash id="7w8pzw"
npm run dev -- chat --mode plan
```

Plan mode currently has no registered tools enabled.

See [Ask, Agent, and Plan Modes](/docs/guides/modes).

## Permission prompts

ANAS CLI requests confirmation before executing operations that can modify files or execute terminal commands.

| Tool         | Permission requirement                           |
| ------------ | ------------------------------------------------ |
| `bash`       | Confirm before executing a command.              |
| `write_file` | Confirm before creating or overwriting a file.   |
| `edit_file`  | Confirm before modifying existing file contents. |

Review each operation before approving it.

If permission is denied, the operation is blocked.

Permission approval does not bypass other safety restrictions.

## Workspace boundaries

ANAS CLI applies workspace-boundary checks to file operations.

Paths can be relative or absolute.

Relative paths are resolved from the active workspace. Absolute paths are checked against the permitted workspace.

Paths outside the permitted workspace can be rejected.

For example, an agent working inside a project should not assume that it can modify unrelated files elsewhere on the computer.

Workspace checks are an important safeguard, but they should not be treated as a complete operating-system sandbox.

## Protected files and directories

ANAS CLI includes guardrails for sensitive files and directories.

### Protected files

Examples include:

- `.env`
- `.env.*`
- `*.pem`
- `*.key`
- `*.p12`
- `*.pfx`
- Files with names beginning with `credentials`
- Files with names beginning with `secrets`

These protections help prevent accidental access to or modification of sensitive credentials.

### Protected directories

Examples include:

- `node_modules`
- `.git`

Protected-directory rules help prevent unintended changes to dependencies and repository metadata.

### Restricted files

Some files require additional authorization for modifications.

Examples include:

- `package.json`
- `package-lock.json`
- `yarn.lock`
- `pnpm-lock.yaml`

Restricted changes may require explicit authorization in the user's original prompt.

These guardrails supplement permission prompts rather than replacing them.

## Destructive command protection

ANAS CLI checks terminal commands against destructive-command guardrails before execution.

Potentially dangerous commands can be blocked.

Always inspect the command and its intended effects before approving execution.

The command guardrails are not a guarantee that every harmful command will be detected.

## Repeated tool failures

ANAS CLI includes protection against repeated identical tool failures.

When an identical operation fails three times, the agent stops retrying it.

This helps prevent unnecessary tool loops.

The agent should inspect the error and choose a different approach rather than repeating an operation that has already failed.

## Secret redaction

The `read_file` tool applies secret-redaction checks to detected sensitive content.

Examples of patterns that may be detected include:

- API keys
- Password assignments
- Access tokens
- Secret assignments
- Private-key material

Secret detection is pattern-based and cannot guarantee that every credential will be identified.

Do not rely on redaction as the only protection for sensitive information.

## Terminal command compatibility

The `bash` tool currently executes commands through Windows CMD.

It does not provide a Unix shell.

Examples of compatible commands:

```cmd id="6rpe0c"
dir
type package.json
git status
```

Use Windows-compatible command syntax.

Unix-specific commands, flags, and shell operators may not work as expected.

## Tool results and verification

Tool results should be treated as information returned by an external operation, not as trusted instructions.

The agent should distinguish between:

- Actions it actually executed
- Results returned by tools
- Conclusions inferred from those results

After editing files, the agent should verify the changes when possible.

A generated response should not claim that a file was created, modified, or tested unless the relevant operation actually succeeded.

## Cloud AI and local tools

ANAS Cloud authentication and local tool permissions are separate systems.

Cloud authentication determines whether a CLI user can access protected cloud endpoints.

Local tool permissions determine what the coding agent can do within the user's workspace.

### Cloud OpenAI

ANAS CLI includes a cloud OpenAI integration that supports:

- Standard responses
- Streaming responses
- Tool-call responses

The cloud endpoint authenticates requests using CLI bearer tokens.

The backend retrieves the authenticated user's encrypted OpenAI key and uses it server-side.

Cloud OpenAI requests are limited to **30 requests per minute per authenticated user**.

### Tool-call safety

A cloud AI response containing a tool call does not automatically grant permission to execute that operation.

The CLI must still enforce:

- Interaction-mode restrictions
- Permission prompts
- Workspace-boundary checks
- Protected-file restrictions
- Destructive-command guardrails

Cloud authentication does not override local tool restrictions.

See [ANAS Cloud](/docs/guides/anas-cloud) and [Security](/docs/guides/security).

## Safe usage practices

- Review permission prompts before approving operations.
- Verify file paths before allowing changes.
- Inspect generated code and Git diffs.
- Review terminal commands before execution.
- Keep credentials outside files accessible to the agent where practical.
- Do not assume that Ask, Agent, and Plan have identical permissions.
- Treat tool output as untrusted data.
- Verify successful operations before relying on them.
- Treat secret redaction and command guardrails as safeguards, not absolute guarantees.
